# Day 02｜A → B 字段需求（待评审）

状态：A 的产品需求草案；真实访谈样本 0，B 尚未评审，**不是数据库 Contract 或实体冻结版**。关联 [访谈提纲](interview-guide.md)、[假设表](hypotheses.md) 与 [主流程草图](../ux/low-fi-flow.md)。

| 信息 | 用户为什么需要 | 空值与来源规则 | A 期待的界面行为 |
| --- | --- | --- | --- |
| 匿名会话标识 | 无账户时继续编辑自己的素材 | 可用随机、不含身份信息的标识；不以姓名/邮箱代替 | 用户能回到自己的草稿，也能删除它 |
| 场景与问题 | 知道回答对应哪一次引导 | 问题版本和输入顺序要可追溯；未回答可为空 | 空白输入和逐步追问可切换、可跳过 |
| 用户原话 | 防止整理过程丢失语境 | 保留原输入；用户删除后不再显示 | 用户可回看、修改原话 |
| 行动/对象/时间 | 把具体经历拆成可检查的信息 | 每个字段都可标“未知”；不要把未知存成 `0`、空字符串或模型猜测 | 未知项明确显示，允许稍后补充 |
| 个人贡献与团队成果 | 避免把团队成绩写成个人功劳 | 分开记录；个人贡献无来源时不确认 | 候选句能够指出哪些词属于个人，哪些是团队结果 |
| 结果与依据 | 判断数字、奖项和影响能否写进简历 | 结果可能未知；数字保留原单位和来源；无法核实不强制填数字 | 用户可删去无法确认的结果，仍能继续 |
| 事实来源 | 从候选内容回到用户原话 | 事实关联源回答或用户手动补充的来源；无来源不得自动确认 | 点击候选句能看见对应原话/依据 |
| 确认状态 | 区分 AI 建议与用户认可的事实 | 建议、待确认、用户确认、用户否定等状态由 B/C 讨论；只有用户操作可将事实标为确认 | 用户逐条确认或拒绝，拒绝后候选句同步更新 |
| 目标 | 同一经历可面向不同岗位/项目改写 | 目标可空，空时采用通用表达；不推断具体学校/岗位要求 | 用户可输入或修改目标，看到改写前后差别 |
| 候选亮点与简历句 | 支持编辑与导出 | 保存与事实/目标的关联及版本；不直接覆盖用户原话 | 用户看到候选、依据、风险提示并能手动改写 |
| 导出内容 | 能拿走成果 | 仅导出用户最终确认的句子；导出时间/格式可记录 | 复制或下载后内容与预览一致 |

## 用两条**虚构**案例检查空值

- S01：只知道“整理了选课信息”，人数、结果均未知。系统应保存个人行动和未知项，不能生成“帮助数十人”。
- S02：知道“负责清洗数据并展示图表”，团队成绩不归个人。系统应允许直接录入、跳过长追问，并分开个人贡献与团队结果。

上述案例只检验字段表达能力；不能代替真实访谈。B 需要确认数据模型、匿名会话过期/删除策略、事实来源关联方式和导出所需字段。A 在 B 的实体草案到达后核对一次界面字段，再变更本表。
