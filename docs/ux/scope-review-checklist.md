# Day 03｜B/C 范围评审清单

这是 A 提供的评审入口，**不是 B/C 已签字的记录**。范围依据 [PRODUCT.md](../../PRODUCT.md)、[NOT_DOING.md](../../NOT_DOING.md) 和 [演示剧本](day03-demo-script.md)。请审阅者在 PR 中留下决定和具体改动意见；A 根据真实反馈修订，再记录三方结论。

## B：数据、接口与 22 天容量

- [ ] 能否用当前仓库架构支持“原话 → 事实来源 → 用户确认 → 目标 → 候选句 → 导出”？指出最慢的依赖。
- [ ] 匿名草稿如何保存、过期、删除？丢失/失效时用户看见什么？
- [ ] Fact 与原回答如何关联？“未知”和“团队成果”如何表示，避免被当作 0 或个人成绩？
- [ ] 只有用户能确认事实的状态变更由谁负责？AI 建议如何留在待确认状态？
- [ ] 复制文本与 Markdown 导出是否可在 P0 做到；若时间不足，建议砍哪些外层功能？
- [ ] PostgreSQL、本机环境、Migration、Contract 与三机启动的负责人及可复现证据是什么？

## C：提问、模型边界与降级

- [ ] [六个访谈问题](../research/interview-guide.md#六个开放问题) 有无诱导数字、领导角色或结果的问法？
- [ ] 模型输出如何标为候选并附来源，不把“主导/显著提升/获奖”当事实？
- [ ] 未知结果、团队归属、无证据数字是否进入 Eval 候选？预期输出是什么？
- [ ] 模型超时或不可用时，静态问题和手动编辑是否仍让 P0 可导出？
- [ ] P1 知识库、RAG 等未完成时，P0 是否独立运行？

## A：收到意见后的冻结条件

- [ ] 用真实访谈记录核对用户问题；保留反例，不把合成案例计为用户证据。
- [ ] B/C 分别给出可接受、需改动或无法在 22 天完成的明确意见。
- [ ] 三方确认同一版 P0 完成定义、延期项与演示剧本；决定写入团队决策记录。
- [ ] 实现后按 [演示剧本](day03-demo-script.md) 运行，记录实际 PASS/FAIL 与证据。

在上述条件满足之前，`PRODUCT.md` 保持“A 提案”，不得称为 Scope Freeze。
